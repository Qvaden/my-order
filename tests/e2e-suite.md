# Этап 11 — полное системное тестирование перед публикацией

Приложение: **МОЙ ПОРЯДОК** (VK Mini App). Дата прогона: 09.11.2026.
Окружение: Chromium (Playwright, headless), `http://localhost:8080`, мобильный вьюпорт 375×812, touch включён.
Результат: **288 проверок, 288 PASS / 0 FAIL**. Найдено 6 критических багов — все исправлены и закрыты регрессионными тестами.

## Как запустить

```
node server.js                 # статический сервер на :8080 (в отдельной консоли)
node tests/01-smoke.mjs        # один набор
node tests/01-smoke.mjs; node tests/02-persistence.mjs; ... ; node tests/10-performance.mjs
```

Каждый набор завершается кодом 0 при успехе и 1 при любом FAIL, печатая построчный
отчёт `PASS/FAIL` с фактическим значением после `→`. Скриншоты и JSON-дампы —
в `%LOCALAPPDATA%\opencode\shots\e11`. Общая инфраструктура (браузер, консольный
страж, сидинг, справочники допустимых значений `REF`) — `tests/harness.mjs`.
Каталог `tests/` намеренно вне precache-списка Service Worker: тесты не попадают в офлайн-кэш.

### Что именно проверено (сокращённо)

**1–2. Базовое и сохранность данных.** Все 7 разделов рендерятся, консоль чиста,
горизонтального скролла на 375 px нет, touch-цели ≥44 px. Добавление → перезагрузка →
значение цело; изменение и удаление тоже переживают перезагрузку; две вкладки видят
одни данные; повторное открытие вкладки из истории не дублирует записи; recurring-шаблоны
не автогенерируют платёжи (счётчики плоские после reload).

**3. Самолечение БД.** Удаление базы из второй вкладки, поднятие версии схемы, `db.close()`,
`InvalidStateError` — приложение восстанавливает соединение и продолжает работать без
перезагрузки. Единственный невозстановимый случай: другая вкладка подняла схему **выше**
`CURRENT_VERSION` — там обязано быть сообщение «более новую версию… Обновите страницу»,
что и проверяется.

**4. Резервные копии.** Структура дампа, совпадение id, размер, кнопка скачивания, статусы.
«Удалить всё» чистит только data-store, служебный `settings` не трогает. Импорт восстанавливает
12/12 записей с теми же id и связями `meter_readings → meters` (сирот 0). Битый JSON, JSON-массив,
дамп без `data`, дамп с незнакомым store — отклоняются **до** записи, данные целы. При сбое в
середине импорта вызывается откат из снимка, пользователь видит ошибку, а не молчаливую пустоту.

**5. Валидация.** Пустые обязательные поля, отрицательные и нечисловые суммы, нулевая сумма,
показание меньше предыдущего (с указанием предыдущего значения в тексте), отрицательное показание,
показание без даты, дата окончания раньше даты выдачи, время без даты в задаче (+ скрытие поля
времени), XSS-инъекции в названиях (хранятся как текст, `script`/`img` в DOM не появляются),
`maxlength=100` и 270-символьные строки без переполнения карточки, сумма `12,50` → `1250` копеек,
разделители тысяч не портят сумму молча. **Строгие даты — см. баг №5.**

**6. Фильтры и сортировка.** Все комбинации фильтров платежей, документов, задач, счётчиков;
сортировка вверх/вниз; активный фильтр подсвечен и синхронен с данными; сброс фильтра
восстанавливает полный список.

**7. Анимации.** Все переходы ≤300 ms, анимируются только `transform`/`opacity`
(композиция GPU), skeleton не «текуч», empty state корректен, collapse при удалении
(регрессия бага №4), pop галочки задачи, `border-left` у предупреждений, blur overlay,
при `prefers-reduced-motion` декоративные анимации выключены. Документ, истекающий
**сегодня**, попадает в предупреждения с формулировкой «сегодня» (регрессия бага №3).

**8. ВКонтакте.** Анти-флеш: `data-theme` и `meta[theme-color]` ставятся инлайн-скриптом
до первого рендера, приоритет `?theme=` над `vk_color_scheme`; фон тёмный сразу, «белой
вспышки» нет. Вне VK `env() === 'browser'`, тема светлая (по критериям этапа), профиля нет.

## Журнал найденных багов

### Баг №1 — потерянное соединение с БД не восстанавливалось (критический)

* **Симптом:** если другая вкладка удаляла базу или поднимала версию схемы, все разделы
  показывали «База данных не инициализирована», кнопка «Попробовать снова» не помогала.
  Данные были целы, но недоступны до перезагрузки страницы.
* **Причина:** `dbConnection` становился `null`/«протухшим», а `window.DB_READY` продолжал
  быть `true`. Проверка флага не проверяла живость соединения, поэтому повторные операции
  падали на том же мёртвом объекте.
* **Исправление:** `js/db.js` — все операции обёрнуты в `withConnection(action)`:
  при `InvalidStateError`/`DatabaseClosedError` выполняется одно `reconnect()` (single-flight
  через `reconnectPromise`, чтобы N упавших операций не открыли N соединений) и **один**
  повтор операции. Повтор безопасен: отменённая транзакция IndexedDB атомарна.
  Функция `isDeadConnectionError` смотрит и на `name`, и на текст сообщения, потому что
  ошибки оборачиваются.
  *Альтернатива — проба-транзакция перед каждой операцией — отклонена: дороже по скорости,
  а выигрыша в надёжности не даёт.*
* **Регрессия:** `tests/03-db-recovery.mjs` (11 проверок) — удалённая база, поднятая версия,
  `close()`, гонка из параллельных операций, невозстановимый случай с более новой схемой.
* **Статус:** исправлен, проверен повторно после всех последующих правок — 11/11.

### Баг №2 — импорт повреждал данные при отказе (критический)

* **Симптом:** дамп с чужим store или с невалидной записью импортировался «наполовину»:
  часть данных терялась, а показывалось «Импортировано: N».
* **Причина:** два дефекта на разных уровнях.
  1. `validateImport` не проверял содержимое `data.data` — незнакомые ключи проходили.
  2. `importDump` **сначала очищал базы**, потом импортировал; при отказе импорта
     пользователь оставался с пустыми данными и без отката.
* **Исправление:**
  1. `js/backup.js` — `validateImport` отвергает неизвестные хранилища в `data.data`.
  2. `js/backup.js` — `importDump` берёт снимок `DB.exportAll()` до очистки и при любой
     ошибке вызывает `restoreFromSnapshot(snapshot)`; пользователь видит ошибку импорта,
     данные целы.
* **Регрессия:** `tests/04-backup.mjs` (32 проверки), в том числе 3.6 «чужой store»,
  3.9 «упавший импорт обязан вернуть данные».
* **Статус:** исправлен, 32/32.

### Баг №3 — документ, истекающий сегодня, не попадал в предупреждения

* **Симптом:** документ с датой окончания «сегодня» не отображался ни в «истекающих»,
  ни в «просроченных» — молчаливая дыра ровно на одном дне.
* **Причина:** `getExpiringSoon` пропускал `d === 0` (`d < 0 → continue` при пороге `d <= threshold`
  с условием, которое ноль не накрывало), а `getExpired` брал только `d < 0`.
  При этом `getStatus` относил ноль к `expiring` — три функции противоречили друг другу.
* **Исправление:** `js/documents.js` — `getExpiringSoon` явно включает `d === 0`
  (комментарий фиксирует противоречие с `getStatus`).
* **Регрессия:** `tests/07-animations.mjs` 6.8.1/6.8.2 — документ, истекающий сегодня,
  виден в предупреждениях, формулировка «сегодня», а не «через 0 дней».
* **Статус:** исправлен.

### Баг №4 — анимация схлопывания карточки не работала ни в одном разделе

* **Симптом:** при удалении карточка исчезала мгновенно, `cardOut` не проигрывался.
* **Причина:** `setupPremiumAnimations()` была определена в `js/app.js`, но не вызывалась.
  Даже после вызова нативный порядок `DB.delete → paint()` мгновенно вытирал исходную
  карточку из DOM — анимировать было нечего.
* **Исправление:** `js/app.js` — `setupPremiumAnimations()` вызывается в `init()`.
  `playCollapse()` клонирует карточку в `position: fixed`-призрак на месте исходной
  (фиксируются `top/left/width/maxHeight`, снимаются все `id`, поля дизейблятся,
  `aria-hidden` + `z-index`), и анимирует уже призрак. Неинвазивно: трогать порядок
  `DB.delete → paint()` в модулях не потребовалось. Призрак обязан исчезнуть из DOM
  по `animationend` (иначе остался бы «лишний» узел).
* **Регрессия:** `tests/07-animations.mjs` (22 проверки) — длительности, GPU-свойства,
  исчезновение призрака из DOM.
* **Статус:** исправлен.

### Баг №5 — календарно-несуществующая дата хранилась и показывалась другой датой (критический, молчаливая порча)

* **Симптом:** `2026-02-31` сохранялась в базу и отображалась в списке как `03.03.2026`.
  Ошибки не было никакой.
* **Причина:** `isValidDate` опирался на JS-парсер: `new Date('2026-02-31')` — **не**
  Invalid Date, а 3 марта (аналогично `2026-04-31` → 1 мая, `2027-02-29` → 1 марта).
  Проверка `!isNaN(...)` такие даты пропускала. Дополнительный слой: `importAll` писал
  записи напрямую, минуя любую валидацию, поэтому файл бэкапа мог занести мусор; поле
  `documents.issuedDate` вообще не было в списке проверяемых.
* **Исправление (два уровня):**
  1. `js/db.js` — `isValidDate` делает строгую календарную проверку: regex `^\d{4}-\d{2}-\d{2}`
     + фактическая длина месяца через `Date.UTC(y, m, 0).getUTCDate()`.
     *Нормализовать значение (переписать 31.02 → 28.02) сознательно отказались: молчаливый
     пересбор даты пользователя — тот же класс дефекта, что и подмена в UI.*
  2. `js/db.js` — `importAll` вызывает `validateData(storeName, record)` для каждой записи,
     а сбойный случай фиксируется как пропуск (`stats.skipped` + `stats.errors`), **не**
     как отмена всей транзакции: одна плохая запись не должна убивать целый импорт.
  3. `DATE_FIELDS.documents` расширен до `['issuedDate', 'expiryDate']`.
* **Регрессия:** `tests/05-validation.mjs` 4.9.1–4.9.8 (9 проверок) — 31.02/31.04/31.06/29.02
  невисокосного/месяц 13/месяц 00 отклоняются; 29.02 високосного 2028 и 1970-01-01 проходят
  без искажения; импорт не может обойти валидацию, при этом целые записи импортируются;
  форма не сохраняет платёж с невозможной датой. Плюс `tests/09-edge-stress.mjs` 8.1.x.
* **Статус:** исправлен, 44/44 в наборе валидации.

### Баг №6 — 10 быстрых кликов «+» открывали 10 одинаковых модалок

* **Симптом:** на тач-устройстве при двойном-тройном тапе по «Добавить» появлялась
  стопка из 5–10 одинаковых окон;
  закрытие одного («Отмена»/Esc/Esc-Esc) оставляло висеть остальные, под затемнённым
  overlay нельзя было добраться до разделов.
* **Причина:** `openModal` в каждом модуле безусловно создавал новый `.modal-overlay`
  и вешал его на `body`.
* **Исправление:** guard по **сигнатуре содержимого** в `openModal` всех пяти модулей
  (`payments`, `meters`, `documents`, `tasks`, `backup`): `overlay._signature = innerHtml`,
  и если уже открыт оверлей с тем же содержимым и без флага `_closing` — повторный вызов
  no-op.
  *Глобальная блокировка «одно окно за раз» отклонена: легитимная вложенность нужна —
  «История показаний» → «Удалить показание?» живёт стопкой из двух разных диалогов.*
* **Регрессия:** `tests/09-edge-stress.mjs` 8.4.1–8.4.4d (8 проверок) — 10 кликов → ровно
  1 окно; закрытие убирает overlay и `modal-open`; спам не создаёт записей; 5 кликов
  «История» → 1 окно; разные диалоги **наслаиваются** (подтверждение открывается поверх
  истории); повторный клик по тому же показанию не множит подтверждений.
* **Статус:** исправлен, 48/48 в наборе.

### Дополнительная правка релиза: версия кэша Service Worker

Все четыре фиксов лежат в файлах, которые `sw.js` отдаёт по **cache-first**. Без смены имени
кэша пользователи получили бы старый JS. `CACHE_NAME`: `myorder-v10-1` → `myorder-v11-1`
(комментарий в `sw.js` объясняет причину; listener `activate` удаляет старые кэши).

## Рекомендации (не блокируют публикацию)

1. **Размер бандла / render-blocking.** 176.7 KB min > порога 150 KB, и из-за отсутствия minify
   мобильный Lighthouse теряет ~15 баллов. Решение не требует трогать логику модулей: отдавать
   min-варианты (esbuild уже подключён как dev-зависимость) и добавить `defer`/`module` для
   независимых модулей. Потенциал: `unminified-javascript` 135 KiB + `unused-css-rules` 58 KiB.
   Для публикации в VK это +15 баллов на мобильной выборке.
2. **`unused-javascript` 110 KiB** — в основном код форм и диалогов разделов, которые на главной
   не нужны. Если размер станет критичен, ленивая загрузка модуля раздела при первом переходе

## Журнал найденных дефектов

### Баг П1 — PIN сохранялся в битый ключ (критический, фича не работала)

В `js/security.js` имена ключей были испорчены на уровне исходника:
`PIN_KEY = '***'` и `UNLOCK_KEY = 'myor…cked'` (вместо `myorder_pin` и
`myorder_pin_unlocked`). Следствие: запись PIN уходила буквально в мусорный ключ,
`isPinSet()` читал её же и «работал», а тест и любое другое место, ожидающее
нормальное имя, не находили данные; разблокировка сессии не сохранялась.

Исправлено: имена приведены к схеме остальных ключей этапа. Проверено 11.7.2–11.7.3
(хэш, соль, отсутствие PINа в открытом виде) и полным циклом «установил → перезапуск
→ блокировка → верный PIN».

### Баг П2 — `PdfExporter.printReport` отсутствовал в публичном API (критический)

`js/backup.js` вызывал `window.PdfExporter.printReport(...)`, а экспорт содержал только
`printReceipt`. Кнопка «Печать отчёта» падала с `TypeError` прямо в консоль
(её ловил консольный страж: `11.16`). Функция в модуле была — её просто не выложили.

Исправлено: добавлен в `window.PdfExporter`. Проверено 11.11.2 (открытый предпросмотр
с тремя таблицами и вызовом печати).

### Баг П3 — данные рендерились под PIN-блокировкой

`gateOnStart()` рисовал оверлей, но `app.js` параллельно отрабатывал роут и вкладывал
платежи в `#app`. Экран был закрыт, а содержимое доступно в DevTools — то есть
блокировка была косметической.

Исправлено: `renderSection()` при `Security.shouldLock()` откладывает раздел
(тот же механизм, что и ожидание БД), `unlock()` рассылает `pin:unlocked`, и
`bindPinEvents()` дорисовывает отложенный маршрут. Проверено 11.7.6: под блокировкой
ни одной видимой карточки, `body overflow: hidden`.

### Баг П4 — русские формы: «21 днь» вместо «21 день»

В `cloud-sync.js` и `backup.js` слово собиралось как `'дн' + plural('ь','я','ей')`,
и форма «день» теряла букву «е» (при 21 дне — «днь»). Проверено 11.6.3 (7/8/11/21/22/24)
и статусом в разделе.

### Баг П5 — подсказка восстановления для короткого VK ID

`recoveryHint()` резал `slice(-4)` только при длине > 4, поэтому аккаунт с `id=1`
показывал «1». Теперь всегда `••••` + последние 4 цифры с дополнением нулями (`••••0001`).

### Баг П6 — кулдаун показывал «Повторите через 0 с.»

Счётчик тикал только в `setInterval` с шагом 500 мс, поэтому первые полсекунды после
пятой ошибки пользователь читал «0 с.» — как будто пауза уже закончилась.
Добавлена немедленная отсечка. Проверено 11.7.8 (остаток > 20 с, кнопка выключена).

### Баг П7 — бары прогноза не анимировались

Ширина ставилась в том же кадре, что и вставка узлов, — transition не запускался.
Перенесено в `requestAnimationFrame`. Проверено 11.3.4 (оба бара имеют ненулевую ширину).

### Баг П8 — тепловая карта: лишняя пустая подпись дней

В шапочке сетки угловая клетка имела класс `.heatmap-day`, поэтому список подписей
начинался с пустой строки. Введён отдельный `.heatmap-corner`.

### Баг П9 — `.heatmap-corner { display: none }` ломал раскладку сетки

Grid-строка теряла первую колонку, и подписи недель сдвигались на колонку дней.

## Что оказалось дефектом тестов, а не приложения

1. **`DB.clear()` требует `confirm=true`** — фикстура звала `clear('payments')`
   и ловила отказ. Правильный вызов — с явным подтверждением.
2. **`goto()` на тот же путь с другим hash не перезагружает страницу**, а блокировка
   PIN навешивается на старте. Тест использовал `goto(.../#payments)` и не видел
   оверлей. Добавлен `reload()`.
3. **UTC vs локальная дата.** Относительные даты фикстур строились как
   `d.toISOString().slice(0,10)` (UTC), а приложение считает «сегодня» по локальным
   суткам (MSK, UTC+3). До полуночи значения совпадали, после — каждая фикстура
   уезжала на день назад, и `06-filters` падал 5 проверками на валидном коде.
   Исправлено во всех наборах и в `harness.seed()`; правка — `tools/fix-test-local-dates.js`.
   Это же чинило `11.3` (прогноз по закрытым месяцам) и `11.4.2`.
4. **Тест сам удалял проверяемый флаг**: в `11.4.2` `removeItem('myorder_cloud_dirty')`
   стоял до чтения значения, поэтому проверка всегда видела `null`.
5. **QR: «пустой код» был ложной тревогой.** Библиотека рисует все модули одним
   `<path>` (это компактная и корректная разметка), поэтому считать число узлов
   бессмысленно — размер кода проверяется по числу команд `M` в атрибуте `d`.
6. **Границы таблиц не видно в `doc.output()` при `compress: true`**: потоки страниц
   уходят в FlateDecode. Для проверки структуры добавлена опция
   `buildReportDoc(report, { compress: false })` — пользовательский файл по-прежнему
   сжимается, тестируется только геометрия.
7. **Лимит VK Storage считали «на глаз»** (120 записей × 400 символов = 80 КБ, что
   ниже реальных 96 КБ, и дамп всё-таки записывался). Теперь порог берётся из
   констант модуля (`CloudSync.VK_LIMIT_CHARS`), фикстура накручивается до фактического
   превышения, а проверка доказывает, что существующая копия **не тронута**.

## Ключевые решения (важно для сопровождения)

**Разделение ответственности.** Гарантированные напоминания отдаёт **системный календарь**:
только он будит человека, когда вкладка закрыта. `push-manager` — второй, «веб-доступный»
слой: он честно работает лишь когда приложение уже открыто. Поэтому `.ics` — основной
механизм этапа, а пуши — дополнительный, и тесты проверяют их по отдельности.

**Экспортированный календарь и пуши обязаны говорить одно и то же.** Отсюда две правки
в списке ниже (баги №1 и №6): у них должен быть одинаковый набор событий.

**Приватность.** `SUMMARY` всегда нейтральный («Платёж», «Дело», «Документ»); названия
записей и суммы появляются только при включённом `showAmounts` (по умолчанию **выключено**).

**Free не видит фичи и не может их вызвать.** Секция настроек скрыта CSS-гейтом
`.pro-only`, а `generateICS()`/`exportNow()`/`checkDueEvents()` отказывают сами
(`reason: 'free'`). Скрытая кнопка — не защита, поэтому проверка идёт на двух уровнях.

## Журнал найденных дефектов

### Баг 12.6 №1 — пуш показывал событие второй раз назавтра и терял четвёртое (критический)

`checkDueEvents` клал в память показов (`markShown`) весь список `fresh`, а показывал
только `fresh.slice(0, MAX_PUSH)`. Следствия: (а) при 4 наступивших сроках четвёртый
не получал напоминания вообще — он «числился показанным» до завтра; (б) в `result`
не было поля `left`, и раздел «Уведомления» утверждал «отправлено 3 из 8», молча
проглатывая пять.

Исправлено: в память идут **только реально показанные** (`covered.forEach(markShown)`);
добавлено поле `left`, `remindLabel` в `backup.js` досказывает «Ещё N сроков — при
следующей проверке». Различены два режима: `force` = «пользователь явно попросил»
(обходит и троттлинг, и память) и `ignoreThrottle` = только троттлинг.
Регрессия: `12.14.6`–`12.14.8`, `12.10.3`.

### Баг 12.6 №2 — просроченный долг выпадал из .ics (критический)

Горизонт выборки считался как `from = сегодня`. Просроченный платёж и невыполненное
прошлое дело приложение напоминает пушем (`overdue` учитывается всегда), но в календарь
они не попадали — то есть главный механизм этапа молчал ровно там, где срок уже нарушен.

Исправлено: нижняя граница — столько же суток **назад**, сколько горизонт вперёд
(`from = horizonEnd(-days)`). Срез по горизонту сохранён, чтобы хвост старых записей
не превращал экспорт в архив. Регрессия: `12.2.5`.

### Баг 12.6 №3 — `isStale()` зависел от облачного флага (критический для правдивости подсказки)

«Календарь отстаёт» загорался, если `CloudSync.isDirty()` был `true`, — то есть из-за
несохранённой в облако копии пользователю предлагалось перевыгрузить `.ics`, который
был актуален.

Исправлено: две собственные метки в `localStorage` — `myorder_calendar_exported` и
`myorder_calendar_changed_at`; `markChanged()` на `db:change` (store `settings`
игнорируется: правка настроек события не меняет), `markExported()` снимает обе,
`isStale()` сравнивает времена. Регрессия: `12.7.1`–`12.7.6`.

### Баг 12.6 №4 — `result0 is not defined`

Обращение к несуществующей переменной в обработчике выгрузки — `TypeError` в консоль
её ломает. Исправлено; набор считает падения консоли FAIL-ом (`12.16`).

### Баг 12.6 №5 — после экспорта сбивался бейдж «показать показания»

`paintReadingBadge(0)` вызывался на пути экспорта, и бейдж гас, хотя показания
не были переданы. Убран лишний вызов; бейдж рисует только сводка главной.
Регрессия: `12.11.4`–`12.11.5`.

### Баг 12.6 №6 — гонка переходов: новый экран затирался старым

`pro:changed` перерисовывает **текущий** раздел. Если в этот момент человек уже ушёл
в другой, отложенный `setTimeout` в `transitionContent` дорисовывал старый раздел
поверх нового. Исправлено токеном перехода (`transitionSeq`): отсталая заявка
отменяется. Регрессия: `12.8.4`, `12.11.8`–`12.11.9`, `12.8.6`.

### Баг 12.6 №7 — асинхронная запись в чужой `#app` из статистики

`onStatsScreen()`/`renderProAnalytics` дописывали PRO-блок в `#app` после того, как
роутер уже увёл пользователя с экрана. Добавлена проверка, что статистика всё ещё
активна. Регрессия: `12.8.5`.

## Что оказалось дефектом тестов, а не приложения

Стоит записать отдельным уроком: **все 14 FAIL последнего прогона до доводки были
неверными ожиданиями теста, а не кодом приложения** (ниже — 11 причин). Настоящие
баги этапа (семь, выше) нашлись раньше, на этапе написания модулей, и были исправлены
до первого же complete-прогона.

1. **BOM не резался.** `replace(/^/, '')` — матч нулевой ширины: регэксп с
   невидимым символом в исходнике не совпал, и первая строка оставалась с префиксом,
   из-за чего падали проверки конверта и `lines[0]`. Теперь есть `stripBom()` по
   кодовой точке (`charCodeAt(0) === 0xFEFF`).
2. **Лишний уровень экранирования.** Проверки `\,`, `\;`, `\\` были написаны как
   `\\\\;` — регулярка требовала два слэша вместо одного.
3. **Проверка формата файлов делалась на закрытых настройках.** При
   `showAmounts=false` в `SUMMARY` нет ни длинных имён, ни спецсимволов — складку
   и экранирование нечем проверять. Собранный отдельно «открытый» дамп
   (`icsSpecials`) используется ровно для этих четырёх проверок.
4. **Два `DESCRIPTION` в блоке — это не баг.** У события их два-три: свой и по
   одному на каждый `VALARM`.
5. **`lines[lines.length - 1]`** — пустая строка после финального CRLF; сравнение
   с `END:VCALENDAR` требовало `filter(l => l !== '').pop()`.
6. **Формат денег.** Разделитель тысяч в `money()` — неразрывный пробел
   (`\u00A0`), а не обычный; проверено через класс `\s`.
7. **Счёт панели снимали после возврата в PRO** — там она всегда 5 пунктов.
   Подсчёт перенесён внутрь Free-фазы того же `evaluate`.
8. **Подмена `window.PushManager.findDueEvents` не работает:** внутри
   `checkDueEvents` вызывается приватная функция модуля, а не поле публичного API.
   Лимит показа проверяется на реальных записях, а ожидание «остаток добирается
   за одну проверку» заменено инвариантом «очередь стекается до нуля» (8 сроков
   при `MAX_PUSH=3` уходят за три проверки, и `shown` в сумме равен `items`).
9. **`App.navigate('home')` на том же маршруте не перерисовывает** (нет
   `hashchange`), поэтому бейдж/панель в тестах обновляются прямым
   `App.renderSection('home')`.
10. **Тест сам себе занимал окно троттлинга:** правки данных перед
    `checkDueEvents` стреляют `db:change`, слушатель которого тоже проверяет
    сроки. В таких местах нужен `ignoreThrottle`.
11. **Бейдж показаний считается по месяцам, а не по датам**: запись на сегодня
    закрывает текущий месяц, и ожидание `hidden === true` верно. Для срочного
    тона нужен второй пропуск — прошлый месяц, поэтому тест добавляет показание
    с `date = сегодня − 40 дней` (в первой декаде месяца это всё ещё «прошлый»).
